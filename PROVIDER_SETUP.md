# Baton credentials and provider setup

Normal users enter their repository URL, GitHub Fine-grained PAT, Gemini API key and a Gemini model identifier in Repository. Validate & Connect proves GitHub credential acceptance, repository access, read endpoints, then Gemini key/model metadata. Users do not configure .env files or require an operator key. They can also connect GitHub alone for context and deterministic exports; AI remains explicitly unavailable until validation.

Both keys stay in tab memory and must be re-entered after reload. The frontend sends X-GitHub-Token, X-Gemini-Key and X-Gemini-Model to Baton over HTTPS. Existing GeminiProvider alone contacts Google with x-goog-api-key; GitHubService alone sends the GitHub credential to GitHub. Keys are not placed in URLs, storage, snapshots, prompts, history, usage or returned JSON. Clearing/replacing the Gemini key invalidates AI history; GitHub replacement revalidates access and clears its quota observations.

POST /api/v1/workspace/provider/validate uses Google's models.get endpoint with a bounded timeout and checks exact model identity plus generateContent support. It does not generate content or certify generation quota/availability. A model metadata check can succeed while generateContent fails: the audit observed this with gemini-2.5-flash-lite. A live two-turn journey subsequently passed with gemini-3.5-flash-lite. That measured result is not a permanent recommendation or a guarantee for another key/account.

GEMINI_API_KEY, GEMINI_MODEL and BATON_ACCESS_KEY remain optional legacy operator configuration, backend only. The legacy server-provider chat path requires the operator key explicitly. User request credentials take precedence and do not need those settings. Never configure VITE_GEMINI or a public operator key. Backend production defaults/CORS permit the canonical frontend; frontend VITE_BATON_API_URL must be the backend origin without /api suffix, queries or credentials.

Usage Center observes provider-reported token fields and actual GitHub counts on existing responses. Missing counts, thinking fields and abandoned operations remain UNKNOWN; metadata validation requests are separate from generation. Stop cancels local waiting and remote work may finish. No automatic billable retry occurs. Key/model metadata, fixtures, HTTP 200 or a deployment marker alone do not certify live response grounding or billing.

For live acceptance, use a selected-repository Fine-grained PAT with Metadata: Read and Contents: Read, validate both providers, analyze explicitly, ask a repository question, inspect original citations and pinned source, ask a follow-up with returned ID/revision, then inspect Usage Center. Backend-only model/schema validation and original evidence rendering remain enforced. See PROJECT_AUDIT.md for exact live local/production boundaries.
